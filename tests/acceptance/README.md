# 烘焙验收（自动判定）

把「烘焙结果像不像华为手机上看到的 HDR」翻译成可计算的指标。跑完直接给 PASS / FAIL，
不需要人看图和口头确认。

## 为什么能这样定标准

手机显示 HDR 时，屏幕的**参考白仍然对应 SDR 的 1.0**。也就是说：

- 画面的暗部、中间调，观感与 SDR 主图**一致**
- 只有超过 1.0 的部分，才显示为「更亮的白」

所以在 SDR 上复现时，正确做法不是把整幅画面按增益图放大，而是
**保持中间调不变，只把高光多出来的部分压回 SDR 范围**。

这条推导直接决定了下面的阈值。

## 指标与阈值

| 指标 | 阈值 | 为什么 |
|---|---|---|
| `median_delta` 中位亮度差 | ±3 灰阶 | 中位落在中间调，必须与源 SDR 一致 |
| `mean_delta` 均值亮度差 | ±5 | 同上，防止整体偏亮/偏暗 |
| `clip_delta` 纯白占比之差 | ≤ +1 个百分点 | 源本身可能有纯白（灯、泡沫），看「比源多多少」；多了就是高光丢层次 |
| `shadow_lift` 暗部提亮 | ≤ 1.10× | 手机显示不会大幅抬暗部 |
| `ssim` 结构相似度 | ≥ 0.90 | 结构不能走样 |
| `sat_ratio` 饱和度增幅 | **0.92 ~ 1.15** | 上限防过艳；**下限防丢 ICC**（v0.1.21 丢 P3 ICC 后掉到 0.873 却全绿，发出去才被用户看出「发灰」） |
| `hl_spread` 高光分位距比 | ≥ 0.45 | 「层次少」的量化（见下节；2026-10-25 晚随双斜率肩由 0.40 上调） |
| `hl_hf` 高光局部对比比 | ≥ 0.75 | 同上（由 0.65 上调） |
| `hf_all` 全图对比比 | ≥ 0.95 | 防整体被磨平（实测最低 1.01；由 0.90 上调） |

## 层次实测（2026-10-25，「层次少」的量化依据）

用户对 0.1.22 的反馈除「发灰」（v0.1.22 已修）外还有「层次少」。把候选指标在
3 个真实样本 × local/wechat/faithful/off × strength 0.40/0.70 上实测：

| 指标 | 定义 | 出货档实测 | off 档实测 |
|---|---|---|---|
| `hl_spread` | 高光区（源 L≥217）内 P95−P50 分位距之比 out/src | **0.42 ~ 0.79**（local@0.70 最低 0.417） | 0.33 ~ 0.80 |
| `hl_hf` | 高光区内梯度能量之比 out/src | **0.69 ~ 1.04**（local@0.70 最低 0.691） | 0.64 ~ 1.04 |
| `hf_all` | 全图梯度能量之比 out/src | 0.98 ~ 1.14 | 0.99 ~ 1.12 |
| `mid_hf`（参考，不入阈值） | 中间调（64≤L<192）梯度能量比 | 0.99 ~ 1.10 | 同左 |

结论：**「层次少」集中在高光区**（软膝 0.96 收敛 + 高光分流的副作用），中间调没丢。
据此定下限：

- `hl_spread_min = 0.40`：贴着出货档实测最低 0.417，先**守住现状**；调参提升后必须上调。
- `hl_hf_min = 0.65`：贴着出货档实测最低 0.691。
- `hf_all_min = 0.90`：贴着实测最低 0.984，拦「整体磨平」类退化。

### 双斜率肩上线后复测（2026-10-25 晚，下限随之上调）

根因定位（两轮诊断实验，`tests/_tmp/sweep2_ceiling.py`，13 组合 × 3 样本）：
样本高光区 HDR 亮度 1.5~1.74× 白点（峰值 2.4×）→ 指数软膝 + 0.96 天花板把它们
全部拍平在 [0.95, 0.96] → `mapped` 的 spread 只剩源的 8%。只调 LTM 参数
（start/detail_gain/range_compress 24 种组合）与保斜率线性肩（36 种）均无效 ——
瓶颈是天花板结构，不是参数。

修复：LTM 换**双斜率肩**（`ltm.py` / `LocalToneMapping.kt` 逐行对齐）——
SDR 带 [highlight_start..1.0] 线性压到 0.93 让出空间，HDR 超白带 [0..1.3]
以小斜率线性延伸到 0.96，ceiling 放开到 1.0（sRGB 250→255 五个灰阶是
「比白更亮」的唯一去处；纯白由 `clip_delta` 阈值看守）。y0 扫描 0.90/0.93/0.95
中 0.93 唯一把最差样本 spread 从 0.417 提到 0.500。

复测（3 真实样本 × local，全门禁矩阵 20/20 通过）：

| 指标 | 旧指数肩（0.70 档） | 双斜率肩（0.70 档） | 双斜率肩（0.40 档） |
|---|---|---|---|
| `hl_spread` | 0.417（恒定） | **0.50 / 0.50 / 0.60** | 0.67 / 0.79 / 0.80 |
| `hl_hf` | 0.690 | **0.78 / 0.80 / 0.89** | 0.93 / 0.96 / 0.97 |
| `hf_all` | 0.984（全档最低） | 1.01 ~ 1.15 | 1.01 ~ 1.08 |

下限随实测上调，且故意落在**旧算法实测值之下**——换回旧肩会被门禁拦住：

- `hl_spread_min` 0.40 → **0.45**（新实测最低 0.50；旧值 0.417 < 0.45）
- `hl_hf_min` 0.65 → **0.75**（新实测最低 0.78；旧值 0.690 < 0.75）
- `hf_all_min` 0.90 → **0.95**（新实测最低 1.01）

边界约定：

- 层次下限只对**出货 profile**（local/wechat/faithful）生效；`off` 是 A/B 对照旧行为，
  不代表出货物性，不参与（其 0.70 档高光分位距低至 0.33，属于旧行为的已知特性）。
- 源高光区 <100 像素、或源高光本身是平坦平台（P95−P50 < 4 灰阶，如合成样本）时
  跳过高光两项 —— 以**源**的分位距为判据，源有层次而输出被压平才是要拦的退化。
- strength 走 **(0.40, 0.70) 矩阵**（docs/07 §2-4）：0.40 是定档基准，0.70 是产品默认，
  之前只验 0.40 意味着出货档从未被验收过。

阈值集中在 `accept.py` 的 `DEFAULT_THRESHOLDS`，改一处即可。

## 用法

```bash
# 合成样本（无隐私、可进 CI）
python tests/acceptance/accept.py

# 追加真实样本（ISO Ultra HDR JPEG，不入库）
python tests/acceptance/accept.py --real /path/a.jpg /path/b.jpg

# 机器可读，便于 CI 解析
python tests/acceptance/accept.py --json

# 记下本次指标作为基准，便于以后对比漂移
python tests/acceptance/accept.py --update-baseline
```

退出码：`0` 全通过，`1` 有失败项。

## 这套标准是怎么逼出算法修正的

改造前（strength 调参 + 全局乘增益）所有用例都 FAIL，且**调 strength 救不回来**：

| 版本 | 中位差 | 结论 |
|---|---|---|
| 原算法 strength 0.70 | +11 ~ +24 | 整体偏亮，用户直接指出「太亮」 |
| 降到 strength 0.40 | +13 ~ +24 | 仍偏亮 —— 增益图全图有值，乘上去必然提亮，`strength→0` 只会连 HDR 一起丢 |
| 加 SDR 亮度加权 | **+0.0** | 暗部/中间调保持原样，只有亮部采信 HDR |
| 软膝收敛到 0.96（不取 1.0） | 纯白 0.00% | 收敛到 1.0 时 0.9~1.0 挤在 0.99+，大片纯白 |
| 去掉线性对比度 1.06 | 纯白 0.00% | 它把接近白的高光推成 255 |

## 注意

- 真实样本含隐私，**不要放进仓库**；用 `--real` 从本地路径传入。
- `synthetic` 用例由 `uhdr.synthetic` 生成，是极端高对比图，比真实照片更容易暴露高光问题。
- 这个验收只看**亮度/结构/色彩统计**，不能替代人眼对纹理、噪点、局部光晕的判断。
  但它能拦住「整体偏亮」「高光爆掉」这类最常发生的退化。
