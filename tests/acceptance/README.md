# 烘焙验收（自动判定）

把「烘焙结果对不对」翻译成可计算的指标。跑完直接给 PASS / FAIL，
不需要人看图和口头确认。

## 两套基准（2026-10-26 起）

烘焙有两条链路，目标不同，基准也必须不同。分派由
`bake.target_mode_for_profile()` 给出（Python / Kotlin 同源）：

| 模式 | profile | 目标是 | 基准 |
|---|---|---|---|
| **display** | `local` / `wechat`（出货默认） | 手机上看到的 HDR 显示效果：整体更亮、高光耀眼 | **可见增强带 + 自然护栏** |
| **sdr** | `off` / `faithful` | 旧行为，明确承诺「不改变整体明暗」 | 「≈底图」老口径（中位 ±3 / 均值 ±5 / 暗部 ≤1.10） |

### 为什么必须分开

2026-10-25 深夜之前全链只有一套「≈底图」口径。它建立在一条技术推导上：
手机显示 HDR 时屏幕参考白仍对应 SDR 的 1.0，所以中间调观感应当与 SDR 主图一致。

推导本身没错，但**用户的参照物不是 SDR 底图，是手机上的 HDR 显示效果**。
两者不是一回事：手机看 HDR 时整幅画面在感知上明显更亮、高光更耀眼。
用「≈底图」去守出货档，结果是门禁把烘焙图死死摁在平坦底图上——
实测出货档（local@0.70）中位亮度仅比底图 +0~+2 灰阶、暗部 1.01~1.04×，
**门禁全绿，用户装机后原话是「灰灰的、没效果」**。

所以：出货档改成「必须真的更亮，但亮得自然」；`off`/`faithful` 保留老口径
（它们是 A/B 对照与「嫌亮」逃生阀，承诺的正是「别改我明暗」）。

## 指标与阈值

### display 档（local / wechat）

| 指标 | 阈值 | 为什么 |
|---|---|---|
| `median_delta` 中位亮度差 | **+10 ~ +45** | 下限拦「没效果」回归（legacy 实测 +0~+2，高一个数量级）；上限拦失控提亮 |
| `mean_delta` 均值亮度差 | **+8 ~ +40** | 同上 |
| `shadow_lift` 暗部提亮 | **1.15 ~ 2.10** | 下限拦「暗部根本没动 = 没效果」。注意方向与 legacy 相反：老口径是 ≤1.10 的**上限** |
| `clip_delta` 纯白占比之差 | ≤ **+1 个百分点** | 源本身可能有纯白（灯、泡沫），看「比源多多少」；多了就是高光丢层次 |
| `ssim` 结构相似度 | ≥ **0.88** | 贴着实测最低（A/local@0.70 = 0.895）|
| `sat_ratio` 饱和度 | **0.90 ~ 1.15** | 上限防过艳；**下限防丢 ICC**（v0.1.21 丢 P3 ICC 后掉到 0.873 却全绿，发出去才被用户看出「发灰」）|
| `hl_spread` 高光分位距比 | ≥ **0.45** | 「高光被拍平」的**主哨兵**，见下 |
| `hl_hf` 高光局部对比比 | ≥ **0.55** | 辅哨兵 |
| `hf_all` 全图对比比 | ≥ **0.92** | 防整体被磨平 |

### legacy 档（off / faithful）

`median_delta` ±3、`mean_delta` ±5、`clip_delta` ≤ +1pt、`shadow_lift` ≤ 1.10、
`ssim` ≥ 0.90、`sat_ratio` 0.92~1.15、`hl_spread` ≥ 0.45、`hl_hf` ≥ 0.75、
`hf_all` ≥ 0.95。**全部保持 2026-10-25 的值，一个没动。**

### 三个下限为什么定在这些数（实测依据）

3 真实样本 × 4 profile × strength 0.40/0.70，`out/visual/diag/calib_new.py`：

| 指标 | display 实测 | 阈值 | 旧算法实测 | 阈值能否拦住旧算法 |
|---|---|---|---|---|
| `hl_spread` | **0.500 ~ 0.800** | 0.45 | 0.417（指数肩，恒定） | **能** |
| `hl_hf` | **0.605 ~ 0.984** | 0.55 | 0.690 | **不能** |
| `hf_all` | **0.946 ~ 1.068** | 0.92 | 0.984 | 不能（本就不用于区分新旧）|

两条结论必须写下来，否则后人会把锅丢错地方：

1. **`hl_spread` 是主哨兵，`hl_hf` 是辅哨兵。** 旧指数肩的 `hl_spread` 恒为
   0.417（< 0.45，被拦），而它的 `hl_hf` 0.690 高于 0.55（拦不住）。
   若把判据只放在 `hl_hf` 上，换回旧肩会静默通过。
2. **`hf_all` 由 0.95 下调到 0.92 是必要的**，不是放宽：display 实测最低
   0.946（C/wechat@0.70）本来就会被 0.95 误拦。display 路径亮度重排更强、
   全图梯度略降属预期；`hf_all` 只负责拦「整体被磨平」（那会掉到 0.85 以下）。

### 边界约定

- 层次下限（`hl_spread` / `hl_hf`）只对**出货 profile**（local/wechat/faithful）
  生效；`off` 是 A/B 对照旧行为，不代表出货物性（其 0.70 档高光分位距低至 0.33，
  是旧行为的已知特性）。
- 源高光区 <100 像素、或源高光本身是平坦平台（P95−P50 < 4 灰阶，如合成样本）时
  跳过高光两项 —— 以**源**的分位距为判据，源有层次而输出被压平才是要拦的退化。
- strength 走 **(0.40, 0.70) 矩阵**（docs/07 §2-4）：0.40 是定档基准，
  0.70 是产品默认。真实样本跑**全 4 个 profile**（此前只跑 local/off，
  而出货档 wechat 从未被真实数据压过）。

## 层次实测（2026-10-25，「层次少」的量化依据）

用户对 0.1.22 的反馈除「发灰」（v0.1.22 已修）外还有「层次少」。把候选指标在
3 个真实样本 × local/wechat/faithful/off × strength 0.40/0.70 上实测：

| 指标 | 定义 | 出货档实测 | off 档实测 |
|---|---|---|---|
| `hl_spread` | 高光区（源 L≥217）内 P95−P50 分位距之比 out/src | **0.42 ~ 0.79**（local@0.70 最低 0.417） | 0.33 ~ 0.80 |
| `hl_hf` | 高光区内梯度能量之比 out/src | **0.69 ~ 1.04**（local@0.70 最低 0.691） | 0.64 ~ 1.04 |
| `hf_all` | 全图梯度能量之比 out/src | 0.98 ~ 1.14 | 0.99 ~ 1.12 |
| `mid_hf`（参考，不入阈值） | 中间调（64≤L<192）梯度能量比 | 0.99 ~ 1.10 | 同左 |

结论：**「层次少」集中在高光区**（软膝 0.96 收敛 + 高光分流的副作用），中间调没丢。

### 双斜率肩上线后复测（2026-10-25 晚）

根因定位（两轮诊断实验，`tests/_tmp/sweep2_ceiling.py`，13 组合 × 3 样本）：
样本高光区 HDR 亮度 1.5~1.74× 白点（峰值 2.4×）→ 指数软膝 + 0.96 天花板把它们
全部拍平在 [0.95, 0.96] → `mapped` 的 spread 只剩源的 8%。只调 LTM 参数
（start/detail_gain/range_compress 24 种组合）与保斜率线性肩（36 种）均无效 ——
瓶颈是天花板结构，不是参数。

修复：LTM 换**双斜率肩**（`ltm.py` / `LocalToneMapping.kt` 逐行对齐）——
SDR 带 [highlight_start..1.0] 线性压到 0.93 让出空间，HDR 超白带 [0..1.3]
以小斜率线性延伸到 0.96，ceiling 放开到 1.0（sRGB 250→255 五个灰阶是
「比白更亮」的唯一去处；纯白由 `clip_delta` 阈值看守）。y0 扫描 0.90/0.93/0.95
中 0.93 唯一把最差样本 spread 从 0.417 提到 0.500。

## 用法

```bash
# 合成样本（无隐私、可进 CI）
python tests/acceptance/accept.py

# 追加真实样本（ISO Ultra HDR JPEG，不入库）
python tests/acceptance/accept.py --real /path/a.jpg /path/b.jpg

# 机器可读，便于 CI 解析（thresholds 现在分 display / legacy 两组）
python tests/acceptance/accept.py --json

# 记下本次指标作为基准，便于以后对比漂移
python tests/acceptance/accept.py --update-baseline
```

退出码：`0` 全通过，`1` 有失败项。

## 这套标准是怎么逼出算法修正的

| 版本 | 中位差 | 结论 |
|---|---|---|
| 原算法 strength 0.70 | +11 ~ +24 | 整体偏亮，用户直接指出「太亮」 |
| 降到 strength 0.40 | +13 ~ +24 | 仍偏亮 —— 增益图全图有值，乘上去必然提亮，`strength→0` 只会连 HDR 一起丢 |
| 加 SDR 亮度加权（legacy 路线） | **+0.0** | 暗部/中间调保持原样，只有亮部采信 HDR |
| 软膝收敛到 0.96（不取 1.0） | 纯白 0.00% | 收敛到 1.0 时 0.9~1.0 挤在 0.99+，大片纯白 |
| 去掉线性对比度 1.06 | 纯白 0.00% | 它把接近白的高光推成 255 |
| **改 display 目标（2026-10-26）** | **+24 ~ +35** | SDR 锚定按设计把增量摁回底图，观感上等于「没效果」。改成让烘焙图带上 HDR 的亮度结构后，「效果」才真的在像素里 |

最后一行是重要教训：**同一批指标，口径错了会得出相反的结论**。
「+0.0 中位差」一度被当成成功（5/5 PASS），实际是观感失败的证据。

## 注意

- 真实样本含隐私，**不要放进仓库**；用 `--real` 从本地路径传入。
- `synthetic` 用例由 `uhdr.synthetic` 生成，是极端高对比图，比真实照片更容易暴露高光问题。
- 这个验收只看**亮度/结构/色彩统计**，不能替代人眼对纹理、噪点、局部光晕的判断。
  它能拦住「整体偏亮」「高光爆掉」「整体没效果」这类最常发生的退化。
- **改阈值前先跑 `out/visual/diag/calib_new.py`** 拿实测范围，再按「贴着实测最低值、
  且必须能拦住已知的旧实现」两条原则定，理由写进 `docs/07-testing-strategy.md`。
