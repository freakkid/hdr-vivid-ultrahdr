# 烘焙验收（自动判定）

把「烘焙结果像不像华为手机上看到的 HDR」翻译成可计算的指标。跑完直接给 PASS / FAIL，
不需要人看图和口头确认。

## 为什么能这样定标准

手机显示 HDR 时，屏幕的**参考白仍然对应 SDR 的 1.0**。也就是说：

- 画面的暗部、中间调，观感与 SDR 主图**一致**
- 只有超过 1.0 的部分，才显示为「更亮的白」

所以在 SDR 上复现时，正确做法不是把整幅画面按增益图放大，而是
**保持中间调不变，只把高光多出来的部分压回 SDR 范围**。

这条推导直接决定了下面的阈值。

## 指标与阈值

| 指标 | 阈值 | 为什么 |
|---|---|---|
| `median_delta` 中位亮度差 | ±3 灰阶 | 中位落在中间调，必须与源 SDR 一致 |
| `mean_delta` 均值亮度差 | ±5 | 同上，防止整体偏亮/偏暗 |
| `clip_delta` 纯白占比之差 | ≤ +1 个百分点 | 源本身可能有纯白（灯、泡沫），看「比源多多少」；多了就是高光丢层次 |
| `shadow_lift` 暗部提亮 | ≤ 1.10× | 手机显示不会大幅抬暗部 |
| `ssim` 结构相似度 | ≥ 0.90 | 结构不能走样 |
| `sat_ratio` 饱和度增幅 | ≤ 1.15 | 没做色域转换时的兜底，防止过艳 |

阈值集中在 `accept.py` 的 `DEFAULT_THRESHOLDS`，改一处即可。

## 用法

```bash
# 合成样本（无隐私、可进 CI）
python tests/acceptance/accept.py

# 追加真实样本（ISO Ultra HDR JPEG，不入库）
python tests/acceptance/accept.py --real /path/a.jpg /path/b.jpg

# 机器可读，便于 CI 解析
python tests/acceptance/accept.py --json

# 记下本次指标作为基准，便于以后对比漂移
python tests/acceptance/accept.py --update-baseline
```

退出码：`0` 全通过，`1` 有失败项。

## 这套标准是怎么逼出算法修正的

改造前（strength 调参 + 全局乘增益）所有用例都 FAIL，且**调 strength 救不回来**：

| 版本 | 中位差 | 结论 |
|---|---|---|
| 原算法 strength 0.70 | +11 ~ +24 | 整体偏亮，用户直接指出「太亮」 |
| 降到 strength 0.40 | +13 ~ +24 | 仍偏亮 —— 增益图全图有值，乘上去必然提亮，`strength→0` 只会连 HDR 一起丢 |
| 加 SDR 亮度加权 | **+0.0** | 暗部/中间调保持原样，只有亮部采信 HDR |
| 软膝收敛到 0.96（不取 1.0） | 纯白 0.00% | 收敛到 1.0 时 0.9~1.0 挤在 0.99+，大片纯白 |
| 去掉线性对比度 1.06 | 纯白 0.00% | 它把接近白的高光推成 255 |

## 注意

- 真实样本含隐私，**不要放进仓库**；用 `--real` 从本地路径传入。
- `synthetic` 用例由 `uhdr.synthetic` 生成，是极端高对比图，比真实照片更容易暴露高光问题。
- 这个验收只看**亮度/结构/色彩统计**，不能替代人眼对纹理、噪点、局部光晕的判断。
  但它能拦住「整体偏亮」「高光爆掉」这类最常发生的退化。
